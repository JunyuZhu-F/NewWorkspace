## 3. 内存、oracle与磁盘

### 含检索：向量文件只是其中一部分

| N | fvecs文件约MiB | C++ float有效载荷MiB | oracle float64矩阵MiB | 三矩阵临时场景MiB |
|---:|---:|---:|---:|---:|
| 10k | 39.10 | 39.06 | 78.13 | 234.38 |
| 25k | 97.75 | 97.66 | 195.31 | 585.94 |
| 50k | 195.50 | 195.31 | 390.63 | 1171.88 |
| 100k | 391.01 | 390.63 | 781.25 | 2343.75 |

这些是模块载荷/场景，**不是进程峰值估计的完整上界**。float64距离表达式可能同时持有输入、差值、平方临时矩阵；NumPy版本/临时复用会影响实际峰值，不声称必然分配三份。100k的该场景已超过2GiB，尚未加解释器/字典/候选/统计，不能直接批准现oracle的100k首批。全量现有C++内存加载器的float有效载荷下界更已超2GiB：ARXIV 11,319,472,128字节、WIKI 7,953,117,184字节；不意味着所有流式/映射方法都不可能，只说明当前实现/预算不相容。

精确字节及每个候选query集合的容量场景见[内存/几何CSV](notes/scale01-assessment-20261027-01/memory-and-geometry-scenarios.csv)、[全量载荷下界](notes/scale01-assessment-20261027-01/full-data-lower-bounds.csv)。

源码审查发现的实际放大项：

1. `load_vectors`逐记录resize，没有预先reserve总量；本机MSVC STL按old+old/2增长，重分配期间旧/新buffer共存。该模块可用约2.5倍float有效载荷作保守场景，不能据此承诺整个进程不超限。STL实现证据见[摘录](notes/scale01-assessment-20261027-01/stl-vector-growth.txt)。
2. `Backend::search`先收集所有保留候选再resize(k)，resize不释放vector容量；`Response`基线跨全部case/probe持有候选及hits容量。不是只缓存每case的10或100个结果。按当前x64 Id=4/Hit=16及本机增长场景，四probe基线有效载荷/容量可粗筛为 `48×Σ候选数` 到 `112×Σ候选数` 字节；不是物理堆界，未计分配器和索引等。
3. WIKI 25k全456查询的基线容量场景约67.81–158.23MiB；固定64查询则约9.79–22.84MiB。50k全查询约134.42–313.64MiB；100k约268.69–626.95MiB。仅减query数不会缩小常驻向量矩阵。
4. scope文本、`read_text().splitlines()`、Python ID列表、精确GT/各run排名及计时池仍占资源。源码中的`fixture()`为每个目录扫描全部条目重算候选数，是O(D×N)，不能只预算矩阵运算。

### 纯目录也有独立判定成本

WIKI目录C++驱动同时持有输入、5份oracle状态及预计算集合，三策略按顺序创建，不是把三个常驻索引相加，也不是只看Roaring portable字节。Python目录核验当前还复用含向量文件的fixture校验和全部检索case生成，不能称为已经分离的纯目录资源链。

O(D×N)参考检查量从10k的230,250,000，增至25k的1,089,725,000、50k的3,458,000,000、100k的10,692,100,000。旧10k目录核验约18秒，简单复杂度场景100k可超过600秒；这不是实测新规模耗时，却说明核验器本身可能先超时。首批应分离纯目录准备/核验，保持独立完整集合判定，不能通过减少必需检查来过预算。

## 4. 时间筛查：是场景，不是跑通证明

计算使用旧命令时间、setup加载/训练及建树区间，再按N、目录/路径载荷、query数和候选总量构造工作比例；oracle另按N×D筛查。2倍压力场景不是置信区间，也不是已验证上界。具体公式及CSV见[分析脚本](notes/scale01-assessment-20261027-01/analyze.py)、[时间场景](notes/scale01-assessment-20261027-01/time-scenarios.csv)。实际需要新N准入来校准，背景负载和结构变化不能靠小样本线性外推证明。

| 候选范围 | worker场景s | 5进程＋核验场景min | 2倍压力min | 首批决定 |
|---|---:|---:|---:|---|
| WIKI 25k纯目录，仅默认 | 161.2 | 14.8 | 29.7 | 推荐受控准入；正式单元30min仍需准入留裕量 |
| ARXIV 25k检索，全501 time query | 86.3 | 7.7 | 15.5 | 后续候选，oracle峰值须实测准入；不是本轮批准 |
| WIKI 25k检索，全456 query | 564.6 | 49.5 | 98.9 | 不直接沿用600s/1800s预算；场景已不合预算 |
| WIKI 25k检索，固定64 query | 90.5 | 9.9 | 19.9 | 后续候选，另版声明子工作负载并准入 |
| WIKI 50k检索，固定64 query | 180.8 | 22.7 | 45.4 | 暂缓，压力场景超30min |

ARXIV纯目录新规模没有同版新驱动的已测时间，不能拿004的34目录时间直接外推成保证；它也要走同一受控准入。WIKI全query场景超限只是筛查否决，不是一次已发生的失败实验。

compact64提案：WIKI query按ID模8分桶，各桶57个ID等间隔选8个，总64，仍按原固定哈希配目录；ARXIV可选按year/month约束各32个等间隔query。该选择独立于文本、qrels和结果，尚未成为实验协议。与旧全query曲线不是同一工作负载，不应不加说明拼成跨规模曲线；若要严格规模因果比较，需要另行冻结共同query集合/范围与必要控制，而不是重命名旧成绩。

## 5. 推荐首批矩阵和必须先做的软件准入

**提案A：25k纯目录，默认API计时，先不扩phase/allocation。** 两个数据集各5个独立进程（共10进程），每进程顺序比较三策略，3预热＋20测量，从同一初始树重建；最多32个真实anchor、两模式最多64case；固定连续4项MOVE/MERGE。保持原方法与catalog包含边界，不将默认时间当目录净时间。phase扩展另作决定，不能把10k诊断比例搬到25k。

查询按可用深度/候选量/fanout预先分层；ARXIV不存在的深度明确不适用，WIKI保留真实深路径。维护选最大合法非根子树及最深末端，确定不包含的目标，先独立oracle验证合法性；具体清单在正式前冻结，不按运行结果换目录。因新层级规模/操作可能与旧矩阵不同，只能作为另版25k工作负载，不自动声称是严格受控规模增长率。

| 预算/前置 | 首批提案，不是旧协议改动 |
|---|---|
| 启动available | ≥4GiB，连续20秒采样确认；当前约2.9GiB未达，不自动关闭用户应用 |
| 运行硬停止 | private>2GiB或available<2GiB即停；每worker600s、每数据集/默认单元1800s；两数据集总上限3600s，不合并为可偷偷超时的单元 |
| 磁盘 | D自由≥10GiB；新增工作空间预留2GiB，每实验输出≤1GiB，保留失败/旧结果 |
| 核验/资源探针 | 独立于正式query计时；observer/oracle也受private/available/600s预算，不能只盯C++worker |
| 先行准入 | 新适配器ASan最多5k确定性输入＋边界；新25k Release一进程/三策略/0预热1pass，完整集合/状态核验，不作性能成绩 |
| 进入5进程条件 | 源/输入/协议冻结、全语义通过；实测private不超过建议1.5GiB准入阈值；按新准入分离setup/pass/oracle重估整单元并留至少20%时间余量（≤1440s场景）；仍受1800s硬停。达不到就停，不自动削减重复/查询/验证或放宽预算 |

以上“硬停止”指软件检测到超限即终止，不是已实现的OS内存配额；现有runner约1秒轮询，可能漏短峰，不能称预留了2GiB或保证绝不超限。新准备建议启动前检查并用≤250ms资源采样，再结合预分配估计/准入裕量；仍不将采样当精确峰值。两个数据集、各worker、oracle必须串行，不为缩短总时间并发叠加资源。当前背景应用不由程序擅自关闭。

目前代码不能直接支持该矩阵：`prepare.py`、C++形状断言、oracle数组与固定23025目录检查写死10k；纯目录prepare还连带提取向量、构建/运行检索准入；`fixture()`的全目录逐条目扫描与全文scope读取也有预算风险。因此下一软件子任务SCALE-PREP-01须在**新隔离版本**参数化规模/清单与核验、分离纯目录路径、加入启动门禁及准入资源采样。保留旧baseline和快照，不全局替换所有10000（有些是时钟校准次数），不改核心目录算法、ANN参数或独立判定语义。本轮没有实施这些代码修改。

随后含检索的提案B才考虑ARXIV 25k全501、WIKI 25k compact64；先确认oracles和输出预算，再冻结新query集合与独立GT、跑准入，然后由用户决定是否正式。nDCG仍不报告，不将原型后端/独立约束冒充作者Viking工作负载。50k/100k仅作元数据几何和资源筛查，未准备向量fixture/索引/GT。
