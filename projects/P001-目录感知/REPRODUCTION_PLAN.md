## 1. 为什么这样安排

这篇论文复现的是三个目录索引方案，不是训练模型。先弄清一个目录应包含哪些 ID、移动后归谁，再写索引；否则跑得快也可能只是漏了候选。之后先测目录成本，最后才接向量搜索，避免把目录错误、ANN 误差和相关性评分混在一起。

数据已在场，但部分“做题规则”缺失：WIKI 查询目录、DSM 操作清单、ARXIV 两套查询用途和 Viking 参数。可以设计独立可重复的替代协议，但要先审核并标注，不能称为作者原始工作负载。

主线：**审核范围 → 数据与语义核对 → 独立判定器 → 三方案正确性 → 小规模目录成本 → 同后端检索 → 审批扩规模 → 逐目标验收**。WIKI 缺口只阻塞对应实验，不妨碍人工小树工作，也不意味着可以静默省略 WIKI 目标。

## 4. 实现与正确性：先小树，再真实数据

建议用 C++ + 同版 Roaring，减少语言和集合实现差异；平台由 REVIEW-01 决定。判定器可以简单、慢，但必须独立于被测索引。不能把判定器内部结构作为某一方案的额外缓存加速基线。

检查至少覆盖：

- 根、空/不存在目录、路径段边界 `/a/` 与 `/ab/`、不同层级直接条目、重复目录名。

- 同祖先/跨分支 MOVE；向量和 entry ID 不变，catalog 与新路径一致，共同祖先不误减/重复加。

- 无冲突 MERGE、同名孩子、深层连续冲突、源/目标根均含直接条目；不丢失、不凭空增加条目，不重复排名。

- 每步比较受影响目录的递归/非递归集合、parent/children、catalog 与式 (1)，不能只检查最终根集合数量。

- 固定种子混合写入/查询/维护序列；规模执行前固定，随机检查不替代确定性边界例子。

- 形成环的 MOVE、根操作、包含关系 MERGE、名称冲突按 SPEC 明确拒绝或有证据的语义执行，不能依赖容器意外覆盖。

初始验证采用串行执行。论文的重叠路径序列化未交代完整读同步和失败回滚；串行测试通过不能写成并发正确性证明。新增并发范围须先改 TASK。

| 风险 | 如何处理 |
|---|---|
| 工作负载缺失 | DATA-01 先查；自建协议需审核并标识，不能假称原始。 |
| 多归属不符单父目录假设 | 先定语义；不能暗加引用计数等改进覆盖原方法。 |
| 基线不公平或过度优化 | 忠实实现先冻结，公共组件一致；优化另列，不拿算法改变解释“工程实现”。 |
| 原文时间排除部分系统成本 | 分列净成本和完整成本；明确 bitmap 复制和 catalog 边界。 |
| 硬件/源码不同 | 保留差异，用同机趋势作有限结论，不规定追平倍数。 |
| 内存不足/换页 | 小规模估计，扩规模单独审批。 |

每类任务的证据：

- 阅读/协议：来源定位、版本、决定与依据；不确定项引用 GAP，不复制全文。

- 实现/测试：源码版本；无 Git 时源码快照/hash；固定输入、种子、命令和实际输出。测试通过不等于论文结果通过。

- 实验：真实启动时才在 EXPERIMENTS 登记；在 `experiments/<真实编号>/` 保存配置快照、输入清单、代码、环境、命令、分段时间、原始结果和日志。失败/中断也保留，不覆盖旧记录。

- 结论：逐 OBJ 写结果与限制。证据失效或验证失败时，重开对应任务并核查下游，而非保留虚假的完成标记。
